## Verdict
Ship with fixes (large). The overall Approach A design is still the right shape, and the repo supports most of the intended plumbing, but design_v1 has several implementation-level mismatches that would cause compile/runtime failures or wrong fork history: nonexistent participant helper names, incomplete participant type widening, a Feed effect ordering bug, missing exhaustive EventKind surfaces, nonexistent CSS variables, and most importantly the raw folder copy will propagate old fork-link events into later forks unless the design changes the copy semantics.

## Verified findings
1. Claim in design_v1.md: section 3.2 creates `sys-fork` with `loadParticipants(p)` and `upsertParticipant(p, ...)`, and section 2.3 says the shared participant type already permits `sys`. What the repo shows: there is no `loadParticipants` or kernel `upsertParticipant`; the exported read helper is `readParticipants` and the write helper is private `writeParticipants` in `packages/kernel/src/participants.ts:141` and `packages/kernel/src/participants.ts:153`. Kernel `Participant.kind` is still `"user" | "agent"` in `packages/kernel/src/project.ts:15`, and shared `Participant.kind` is also still `"user" | "agent"` despite `ParticipantKind` including `sys` in `packages/shared/src/participants.ts:1` and `packages/shared/src/participants.ts:3`. `UpdatedParticipant.kind` is also hard-coded in `packages/kernel/src/participants.ts:72` and `packages/shared/src/participants.ts:45`. Recommended fix: implement `ensureSystemForkParticipant` inside `participants.ts` using `readParticipants` plus the private `writeParticipants`, or add a real local upsert helper there; widen kernel and shared `Participant` and `UpdatedParticipant` to include `sys`.

2. Claim in design_v1.md: the route snippet passes `sourceSlug: deriveSlug(sourceSessionId)`. What the repo shows: no `deriveSlug` symbol exists; the only local derivation is inline inside `forkSessionFolder` via `input.sourceSessionId.replace(...)` in `packages/kernel/src/sessions.ts:123`. Recommended fix: either add a local `slugFromSessionId(id)` helper in `routes/sessions.ts`, return the source slug from `forkSessionFolder`, or look up the source `SessionMeta` before forking.

3. Claim in design_v1.md: `forkP: p // same path in v1; widen when cross-path forks land`. What the repo shows: this simplification is correct for the current route. `body.path` selects and activates the project root before the fork in `packages/kernel/src/routes/sessions.ts:314`, and `forkSessionFolder` takes one `Paths`, verifies the source session inside that same root, and allocates the fork inside that same root in `packages/kernel/src/sessions.ts:116`. It is not a cross-destination fork API today. Recommended fix: keep `forkP: p`, but reword the design to say that `body.path` selects the source project's root; current forks are always same-root, so `other_path` remains unset in v1.

4. Claim in design_v1.md: the timestamp-aware writer lets both link writes share starting timestamp `T`, while collision bumps may diverge by a few milliseconds. What the repo shows: the writer currently starts from `isoTimestamp()` and bumps only on same-session `EEXIST` collisions in `packages/kernel/src/events/writer.ts:55` and `packages/kernel/src/events/writer.ts:69`; event records get their display timestamp from the filename in `packages/kernel/src/events/reader.ts:68`. Recommended fix: the design's asymmetry is acceptable, but phrase the invariant as "same requested starting timestamp" rather than "same actual timestamp", and add a writer/fork-link collision test that expects source and fork filenames to diverge only on collision.

5. Claim in design_v1.md: `writeForkLinkPair` accepts `bus: Bus | null` but calls `publishEventWrite(bus, sessionId, ...)`. What the repo shows: `publishEventWrite` requires a non-null `Bus` and a record with `filename`, `kind`, and `participantId` in `packages/kernel/src/services/eventPublisher.ts:4` and `packages/kernel/src/services/eventPublisher.ts:11`. Recommended fix: guard `if (input.bus !== null)` before publishing and pass exactly `{ filename, kind: "fork-link", participantId: SYS_FORK_PARTICIPANT_ID }`.

6. Claim in design_v1.md: a `fork-link` event is never copied across sessions because the copy completes before either current link write. What the repo shows: `forkSessionFolder` recursively copies the entire source session directory with no filter in `packages/kernel/src/sessions.ts:147`. After the first fork, the source session will contain a source-side `*_sys-fork.fork-link.json`; a second fork from that source, or a fork-of-a-fork, will copy that old marker into the new fork before writing the new `from` marker. Recommended fix: explicitly make fork-link events non-copyable. Add a filter or cleanup to `forkSessionFolder` that excludes existing `fork-link` event files, keep `copied_entries` consistent with that exclusion, and add tests for a second fork from the same source and a fork from an existing fork.

7. Claim in design_v1.md: the Feed restore effect can add `itemKey` to the dependency list and remain located where the current restore effect is. What the repo shows: `itemKey` is currently declared after the restore and IntersectionObserver effects in `packages/renderer/src/shell/Feed.tsx:176`; referencing it in the earlier effect's dependency array would hit the temporal dead zone during render. The proposed snippet also sets `restoredSessionRef.current` before checking `scrollRef.current`, so a null root would permanently skip the seed/scroll. Recommended fix: move the `itemKey` `useCallback` above the restore effect, get `root` before setting `restoredSessionRef.current`, and only mark restored after the first-open seed/scroll or saved-anchor attempt is actually possible. The IntersectionObserver race is otherwise OK: the restore effect is declared before the observer in `packages/renderer/src/shell/Feed.tsx:132` and `packages/renderer/src/shell/Feed.tsx:149`, and `markSeen` is monotonic in `packages/renderer/src/state/store.ts:734`.

8. Claim in design_v1.md: the first-open Feed rule should run exactly once even if items arrive in two batches. What the repo shows: current session loading uses one full `listEvents` -> `setEvents` fetch in `packages/renderer/src/App.tsx:254` and later WebSocket refreshes append via `upsertEvent` in `packages/renderer/src/App.tsx:365`; there is no pagination/incomplete initial batch today. Recommended fix: keep the once-per-session behavior for the current repo, but document that later live batches should not be blanket-marked read; they should be read only through follow-mode visibility or user scroll.

9. Claim in design_v1.md: `.fork-link-card` can use `--border-subtle`, `--surface-1`, and `--ink-1`. What the repo shows: the theme tokens define `--canvas`, `--panel`, `--panel-2`, `--ink`, `--ink-2`, `--ink-3`, `--line`, and `--line-2` in `packages/renderer/src/themes/tokens.css:4`; the named variables in the design do not exist. Recommended fix: use existing tokens such as `border: 1px solid var(--line-2)`, `background: var(--panel)` or a light `color-mix` with `--canvas`, label `var(--ink-2)`, and slug `var(--ink)`.

10. Claim in design_v1.md: adding `fork-link` to `RightLog` and `log-filter-types` covers the exhaustive renderer maps. What the repo shows: those two files do need updates (`KIND_ICON`/`KIND_LABEL` are `Record<EventKind, ...>` in `packages/renderer/src/panels/right/RightLog.tsx:44`, and `FILTERABLE_KINDS` is in `packages/renderer/src/popovers/log-filter-types.ts:35`), but there is another exhaustive `Record<EventKind, string>` in `packages/renderer/src/render/BlockAccordion.tsx:37`. Recommended fix: add `fork-link` to `BlockAccordion` or change that map to a `Partial<Record<EventKind, string>>` with fallback, and add the file to section 9.

11. Claim in design_v1.md: `aggregate.ts` has a `feedConversation` whitelist at lines 231-244. What the repo shows: `feedConversation` is a filter expression inside the `aggregate()` function, not a separate exported array, and the whitelist is the boolean return at `packages/renderer/src/state/aggregate.ts:231`. `feedDocument` separately admits named anchors and flow only in `packages/renderer/src/state/aggregate.ts:226`. Recommended fix: add `e.kind === "fork-link"` to the boolean in `feedConversation`; leave `feedDocument` unchanged.

12. Claim in design_v1.md: `ForkLinkCard` should follow the `Sessions.tsx` cross-path switch pattern, but the snippet leaves it as a comment. What the repo shows: the real sequence is `setActivePath`, `setPathsState`, `listSessions` plus `listParticipants`, `setSessions`, `setParticipants`, then `setCurrentSession` in `packages/renderer/src/panels/Sessions.tsx:195` through `packages/renderer/src/panels/Sessions.tsx:207`. Recommended fix: spell out those store selectors and calls in the design and test them, not just the `setActivePath` then `setCurrentSession` pair.

13. Claim in design_v1.md: route tests can live in `packages/kernel/tests/routes/sessions.test.ts`, and the file-by-file list says `forkLinks.test.ts` or extend `sessions.test.ts`. What the repo shows: `packages/kernel/tests/routes/sessions.test.ts` exists but has no fork-route describe block in `packages/kernel/tests/routes/sessions.test.ts:19`; the helper-level `packages/kernel/tests/sessions.test.ts:8` also has no fork coverage. Recommended fix: bootstrap a new `describe("POST /sessions/:id/fork")` in `routes/sessions.test.ts` or create a new route test file; do not assume an existing fork block.

14. Claim in design_v1.md: tests cover the necessary old "source untouched" fallout. What the repo shows: the phase 17 hot runner currently asserts the fork snapshot equals the pre-fork source snapshot and then asserts the source snapshot is unchanged after fork in `packages/kernel/tests/hot/phase17-session-fork-hot.mjs:604` and `packages/kernel/tests/hot/phase17-session-fork-hot.mjs:608`; it later uses the post-fork source snapshot as the invariant for MCP writes in `packages/kernel/tests/hot/phase17-session-fork-hot.mjs:626`. Recommended fix: update the hot runner to allow exactly the new source-side `fork-link(to)` event, to expect the fork-side `fork-link(from)` event, and to exclude non-copyable old fork-link events from copy comparisons.

## Missing or under-specified
- Existing `sys-fork` conflicts are not defined. Today `registerAgent` accepts any ID matching `^(us|ag|sys|grp)-...` in `packages/kernel/src/participants.ts:52` and `packages/kernel/src/participants.ts:233`, so a project could already have `sys-fork` as an agent. The design should say whether `ensureSystemForkParticipant` errors, repairs, or reserves/overwrites that ID.

- The new system participant will enter the global participant map. Some UI intentionally filters to agents/users, but todo assignment currently lists every participant in `packages/renderer/src/compose/CreateTodoPopover.tsx:75` and `packages/renderer/src/cards/TodoItem.tsx:82`. The design should say `sys` participants are hidden from assignee and mention pickers unless a UI explicitly opts into system actors.

- The design does not say how link-write failure tests will simulate source-only or fork-only failures now that `writeForkLinkPair` is a direct imported service that "never throws". It should call out either service-level unit tests for partial failures or a mockable route dependency.

- `RightLog.shortSummary` will fall back to the raw kind for `fork-link` in `packages/renderer/src/panels/right/RightLog.tsx:152`. That is not a compile bug, but the log will be more useful if the design specifies a summary like `Forked to <slug>` / `Forked from <slug>`.

- Add a small writer test for explicit `timestamp` input. Section 8.2 covers concurrent forks, but the lower-level refactor in `packages/kernel/src/events/writer.ts` deserves a direct test that a fixed timestamp is used and collision-bumped.
