## Approach pick

Pick A: Server-driven, EventKind-based, with a small adjustment to make read-anchor seeding client-side/generic rather than dependent on the fork response. The prior "source session untouched" constraint is still respected in spirit if it meant "do not keep driving the source AGENT runtime or append agent-authored work there"; a single `sys-fork` timeline event is deliberately system-authored session history, not runtime handoff content. A is the only option that keeps the fork and source views symmetric: the same `fork-link` event kind, payload, participant, card, read path, and bus behavior apply in both directions. It also fits the current storage model: events are timestamp-sortable files (`packages/shared/src/filenames.ts:10-17`), reads parse arbitrary JSON event payloads (`packages/kernel/src/events/reader.ts:19-35`), and the renderer already dispatches cards by `event.kind` (`packages/renderer/src/cards/EventCard.tsx:92-183`). A can reuse the existing `event_added` path for live source-window updates because event writes publish only `session_id`, filename, kind, and participant (`packages/kernel/src/services/eventPublisher.ts:16-23`), and `App.tsx` already refetches the active session on matching `event_added` (`packages/renderer/src/App.tsx:362-383`). It avoids Approach B's extra `.forks.json`, synthetic insertion rules, and new bus shape, all of which are extra plumbing for a durable thing the app already models as events. Approach C reduces one fork-side write, but it buys that with an asymmetric renderer path and leaves the source-side card as a different truth source from the fork-side card. Legacy compatibility is naturally clean in A: old forks without the new event just render no card, which matches the locked no-backfill decision.

## Critique of the winning approach

1. Failure modes after the directory copy are real because the copy and two event writes are not atomic across directories. Today `forkSessionFolder` creates the new directory and `.fork.json` before returning (`packages/kernel/src/sessions.ts:116-169`), and the fork route would catch later errors as a request failure if the link writes live in the current `try` block (`packages/kernel/src/routes/sessions.ts:356-425`). If the source `fork-link(to)` write fails, the system has a valid legacy-style fork with `.fork.json` but no cards. If the source write succeeds and the fork `fork-link(from)` write fails, the source points to a fork that lacks the symmetric return card. The invariant should be defined explicitly: `.fork.json` plus the copied directory is the canonical fork, while link events are durable UX markers that can be missing only on write failure.

2. The shared timestamp T is the right human model. The source and fork have separate event directories, so the two markers do not need distinct timestamps for sorting. Same T makes the two cards describe one fork instant and lets the source card sit chronologically at that point. The implementation detail is that filenames are sortable to milliseconds and include participant plus kind (`packages/shared/src/filenames.ts:10-17`), so concurrent forks from the same source in the same millisecond could collide on `T_sys-fork.fork-link.json`. The current generic writer always chooses `isoTimestamp()` internally and bumps only on same-session filename collision (`packages/kernel/src/events/writer.ts:40-76`), so A needs a timestamp-aware write helper rather than two ordinary event writes that happen a few milliseconds apart.

3. `sys-fork` should be ensured idempotently on every fork, just before writing the fork-link events. Creating it at server boot would mutate projects that never fork; creating it only "once ever" does not work because participants are per project path. The kernel already accepts `sys-` IDs in its participant ID regex (`packages/kernel/src/participants.ts:52`) and treats non-agent participants as unbound in `listParticipants` (`packages/kernel/src/participants.ts:183-200`), but the persisted kernel `Participant` type still says `kind: "user" | "agent"` (`packages/kernel/src/project.ts:15-20`) while the shared union includes `"sys"` (`packages/shared/src/participants.ts:1`). That means the implementation needs an explicit `ensureSystemForkParticipant(p)` helper and type widening, not `registerAgent`.

4. The anchor seeding rule must run after events arrive, not during navigation or immediately after `setCurrentSession`. `setCurrentSession` intentionally clears events (`packages/renderer/src/state/store.ts:598-625`), and `Feed` only has meaningful item filenames after `events` are aggregated and projected (`packages/renderer/src/shell/Feed.tsx:40-72`). The right insertion point is the existing restore effect around `restoredSessionRef` (`packages/renderer/src/shell/Feed.tsx:132-147`): once `currentSessionId` is set and `items.length > 0`, if `lastSeenBySession[currentSessionId]` is undefined, mark the highest event filename as seen and scroll the feed container to `scrollHeight`. The current effect sets `restoredSessionRef.current` before it checks `savedAnchor` (`packages/renderer/src/shell/Feed.tsx:132-138`), so the new branch should be ordered carefully to avoid marking the session restored before the seed/scroll happens.

5. `latest_filename` in the fork response is not necessary for the locked generic rule. If the server writes `fork-link(from)` into the fork dir last, then its view of the fork's latest filename is correct at response time, assuming no concurrent writer lands later. But pre-seeding from the response is less general than using the events that the client actually loaded, and it does not by itself guarantee bottom scroll because the current restore path scrolls a saved anchor into the center (`packages/renderer/src/shell/Feed.tsx:140-146`). I would omit `latest_filename` unless another caller needs it; if it stays, treat it as an optimization only, not the source of truth for read state.

6. Cross-path card clicks should reuse the existing explicit path-switch pattern. The client has `setActivePath(path)` (`packages/renderer/src/api/client.ts:130-134`, `packages/renderer/src/api/client.ts:300-305`), and `Sessions.tsx` already switches path, refreshes sessions/participants, then selects the target session (`packages/renderer/src/panels/Sessions.tsx:187-213`). A `ForkLinkCard` click with `other_path` should follow that same sequence before `setCurrentSession(other_session_id)`. One gotcha is that the fork route's `body.path` handling activates a path internally (`packages/kernel/src/routes/sessions.ts:314-336`) but does not use the `/paths/active` route's `path-switched` broadcast (`packages/kernel/src/routes/paths.ts:151-169`), so card navigation should not rely on `session.forked` or ambient path state.

7. The card UI should not visually compete with prose cards, access requests, or tool/subagent boxes. `TurnEndDivider` is a low-contrast separator with mono uppercase text and lines (`packages/renderer/src/cards/TurnEndDivider.tsx:13-30`, `packages/renderer/src/cards/cards.css:1398-1463`), while `AccessRequestCard` intentionally uses warning/action styling (`packages/renderer/src/cards/cards.css:1829-1851`) and `ToolUseCard` uses a framed utility panel (`packages/renderer/src/cards/cards.css:1731-1743`). The fork-link card should be a quiet, clickable inline system banner: small icon, "Forked from/to session X", timestamp optional, soft border/background, no participant stripe, no warning colors, and a clear focus state. It should use `button` semantics if the whole surface navigates.

8. `aggregate.ts` will let a new unknown top-level kind into the Everything feed, but the renderer would currently render an empty feed item. `aggregate` includes all visible non-comment, non-choice, non-consumed events in `feed` (`packages/renderer/src/state/aggregate.ts:220-225`), but `feedConversation` whitelists only known conversational kinds (`packages/renderer/src/state/aggregate.ts:231-244`) and `EventCard` returns `null` for unknown kinds (`packages/renderer/src/cards/EventCard.tsx:176-183`). So `fork-link` slots in cleanly only if it is added to `EventKind`, `EventCard`, and probably `feedConversation` if the card should appear outside Everything view. Adding a new `EventKind` will also require updating exhaustive renderer maps such as `RightLog`'s `KIND_ICON`/`KIND_LABEL` (`packages/renderer/src/panels/right/RightLog.tsx:42-74`) and the log filter kind list (`packages/renderer/src/popovers/log-filter-types.ts:29-49`).

9. The test surface should focus on kernel durability and the one renderer state race. `packages/kernel/tests/routes/sessions.test.ts` exists and already covers session route behavior but has no fork route unit tests in the visible portion (`packages/kernel/tests/routes/sessions.test.ts:19-435`), so add route tests that assert the source gets exactly one `fork-link(to)`, the fork gets one `fork-link(from)`, both payloads point at the other session, `.fork.json` is still written, `sys-fork` is created idempotently, and the source marker is not copied into the fork. Add a collision/concurrency-ish test for fixed T if the writer helper supports it. On the renderer side, the most valuable small test is a `Feed` or store-facing test that a first load with no `lastSeenBySession[sid]` seeds to the highest loaded filename and suppresses unread UI; a minimal `EventCard`/`ForkLinkCard` click test is useful for the cross-path path-switch sequence.

10. The current shared type shape needs one more payload contract, not just a union string. `EventKind` is currently the finite union in `packages/shared/src/events.ts:1-14`, `AnyEventRecord` has typed event variants plus a broad `EventRecord` catch-all (`packages/shared/src/events.ts:403-417`), and route response contracts are in `packages/shared/src/eventContracts.ts:19-24`. Add `ForkLinkPayload` and `ForkLinkEventRecord` beside the other event records so renderer code does not have to cast a raw object everywhere.

## Recommended adjustments

1. Keep Approach A, but drop `latest_filename` from the required design. Implement the generic Feed-side first-load rule after events arrive: if no saved anchor exists for the current session, seed to `agg.events.at(-1)?.filename`, scroll the feed container to bottom, set follow mode true, and mark the session as restored.

2. Add a small kernel service/helper for fork-link writes instead of routing through public REST event endpoints. It should ensure `sys-fork` idempotently, write JSON `fork-link` files with a caller-provided timestamp T, return the actual filenames, and publish `event_added` for both sessions after successful writes.

3. Widen participant persistence/types for system participants and add `ensureSystemForkParticipant(p)`. Use fixed id `sys-fork`, name like `Fork`, kind `sys`, and a muted neutral color that will not be confused with user/agent ownership.

4. Treat fork creation as successful once `forkSessionFolder` has completed. If either link write fails, avoid returning a plain failed fork response that hides an already-created fork from the caller; either return success with warnings and no card guarantee, or add carefully bounded compensation for the just-written marker file. Preflight participant creation before the copy to remove the most likely avoidable failure.

5. Add `ForkLinkPayload` with `direction`, `other_session_id`, `other_session_slug`, and optional `other_path`, then update `EventKind`, event reading/writing, `EventCard`, `aggregate.feedConversation`, `RightLog`, and log filtering.

6. Build `ForkLinkCard` as a quiet system navigation row, visually closer to `TurnEndDivider` than to `AccessRequestCard`. Use `GitFork` from lucide, keep the copy short, include a hover/focus state, and route clicks through the existing cross-path switch sequence used by `Sessions.tsx`.

7. Update fork tests and any hot assertions that previously expected the source session tree to be byte-for-byte unchanged after fork. The new invariant is "no agent-authored/runtime continuation in source; exactly one system fork-link event may be appended to source."
