# Review 1 - Fix #2 Access Request Body

Scope note: reviewed only the Fix #2 surface requested: `packages/kernel/src/hooks/autoStream.ts`, `packages/kernel/tests/hooks/autoStream.test.ts`, `packages/renderer/tests/cards/accessRequest.test.tsx`, and `packages/renderer/src/cards/AccessRequestCard.tsx`. I also checked the MCP tool schemas in `packages/kernel/src/mcp/tools.ts` to compare the fallback keys against actual F-Mark tool inputs. I did not run the suites for this review.

## Findings

1. **Correctness: the fallback key list does not actually cover every current F-Mark MCP write shape.**
   `ACCESS_REQUEST_MESSAGE_KEYS` claims it matches the F-Mark MCP surface and says "html -> `body`" (`packages/kernel/src/hooks/autoStream.ts:131-143`), but `fmark_post_html` takes `html`, not `body` (`packages/kernel/src/mcp/tools.ts:638-647`). An HTML call without a `title` will therefore go to the JSON preview path instead of showing the meaningful HTML field. Similar "meaningful-but-outside-list" cases exist for `fmark_post_tool_use.tool_name` / nested `input` (`packages/kernel/src/mcp/tools.ts:482-494`), `fmark_post_file_ref.path` when `description` is absent (`packages/kernel/src/mcp/tools.ts:681-690`), `fmark_post_choice.choices_id`/`selected` (`packages/kernel/src/mcp/tools.ts:566-574`), and non-post tools such as `fmark_read_event.filename` (`packages/kernel/src/mcp/tools.ts:253-261`). The JSON fallback means these are not empty, but "always useful" is too strong. Suggest either adding the missing obvious string keys (`html`, `path`, `filename`, `name`, `tool_name`) or, better, a small tool-name-aware preview table for the F-Mark MCP tools where generic priority can choose the wrong field. At minimum add tests for `fmark_post_html` without `title`, `fmark_post_file_ref` without `description`, and `fmark_post_tool_use` with nested `input.command`.

2. **Correctness/UX: Gemini MCP ToolPermission cards still prefer the generic Gemini message over useful details.**
   In the Gemini branch, `message` is `stringField(payload, "message") ?? pickAccessRequestMessage(details, command)` (`packages/kernel/src/hooks/autoStream.ts:233-235`). Actual Gemini ToolPermission payloads include a generic message like "Tool Confirm MCP Tool Execution requires MCP" plus useful `details` such as `toolName`/`toolDisplayName` for MCP prompts or `command` for shell prompts. Because the top-level message wins, the new symmetric fallback will usually be bypassed for Gemini no-command MCP prompts. This does not appear to break existing Gemini shell behavior because `command` is still copied (`packages/kernel/src/hooks/autoStream.ts:219`, `packages/kernel/src/hooks/autoStream.ts:238`) and the renderer prefers `<pre>` command output (`packages/renderer/src/cards/AccessRequestCard.tsx:115-119`). But it also does not improve Gemini MCP card bodies. Suggest either adding `toolName`/`toolDisplayName` to the detail picker and using details before the top-level generic message for non-command Gemini prompts, or explicitly leaving Gemini unchanged and documenting that the fallback is Claude/Codex-oriented. Add a Gemini MCP no-command test.

3. **Edge-case claim: circular refs are caught only for the preview, not for the event that gets posted.**
   `JSON.stringify(toolInput)` is inside a `try/catch` (`packages/kernel/src/hooks/autoStream.ts:160-166`), so the preview does not throw. But the returned payload still includes the original `tool_input` (`packages/kernel/src/hooks/autoStream.ts:194`, `packages/kernel/src/hooks/autoStream.ts:237`) and `raw` (`packages/kernel/src/hooks/autoStream.ts:209`, `packages/kernel/src/hooks/autoStream.ts:246`), and `postAccessRequest` later stringifies the whole body (`packages/kernel/src/hooks/post.ts:8-16`, `packages/kernel/src/hooks/post.ts:87-96`). Real hook stdin comes from `JSON.parse`, so circular refs cannot occur in production. Still, if `extractAccessRequest` is exported as a pure helper, a direct caller can pass circular input and get a payload that later cannot be posted. Suggest either state/test the JSON-parse-only assumption, or sanitize/omit unserializable `tool_input` and `raw` if this helper is meant to be robust independently.

## Edge Cases

- **Undefined/null `tool_input`:** handled safely. `stringField` returns `undefined` for null/non-object input (`packages/kernel/src/hooks/autoStream.ts:118-122`), and `pickAccessRequestMessage` returns `undefined` (`packages/kernel/src/hooks/autoStream.ts:151-152`). The card falls through to the no-body branch (`packages/renderer/src/cards/AccessRequestCard.tsx:115-119`). A unit test would make this contract explicit.
- **Deeply nested input:** not searched. The helper checks only top-level string fields (`packages/kernel/src/hooks/autoStream.ts:153-156`), so shapes like `fmark_post_tool_use.input.command` rely on JSON fallback. That is acceptable as an escape hatch, but it is less good than a tool-use-specific preview.
- **Buffer/large objects:** real hook input is JSON, so Buffer objects are not expected. For direct calls, `JSON.stringify(Buffer)` can produce a very large byte-array object, and large JSON is fully materialized before the 800-char slice (`packages/kernel/src/hooks/autoStream.ts:160-164`). Also, the cap applies only to `message`; full `tool_input` and `raw` are still posted. So the comment that the cap prevents huge `tool_input` from blowing up event JSON is misleading (`packages/kernel/src/hooks/autoStream.ts:157-159`).

## Truncation

The `…` suffix is honest enough for display (`packages/kernel/src/hooks/autoStream.ts:164`), and token-boundary truncation is not required for correctness because the result is no longer valid JSON once the ellipsis is appended. The current slice can cut mid-key or mid-string, which may make the preview look more authoritative than it is. A nicer display-only compromise would be: cut at the last comma before the limit when possible, then append `…`, or prefix/suffix with a clearer marker such as `[truncated]`. More importantly, tests should assert the capped preview still includes early useful keys, not just length and suffix (`packages/kernel/tests/hooks/autoStream.test.ts:317-330`).

## Test Gaps

- Kernel tests cover the reported happy paths and JSON fallback (`packages/kernel/tests/hooks/autoStream.test.ts:236-383`), but they do not cover `fmark_post_html`, `fmark_post_file_ref`, `fmark_post_tool_use`, null/undefined `tool_input`, circular/direct-call behavior, or Gemini MCP details with no `command`.
- Renderer tests cover the three body branches and callbacks (`packages/renderer/tests/cards/accessRequest.test.tsx:46-184`) plus a responded/closed request via an access-response event (`packages/renderer/tests/cards/accessRequest.test.tsx:186-221`). They do not cover request statuses such as `approved`, `denied`, or `expired` without a response event, nor an expired access-response. Those states matter because `statusLabel` and `open` are computed separately (`packages/renderer/src/cards/AccessRequestCard.tsx:46-52`, `packages/renderer/src/cards/AccessRequestCard.tsx:78-82`).
- The access-card store integration is still uncovered. `pendingAccessCountForParticipant` (`packages/renderer/src/cards/AccessRequestCard.tsx:36-43`) feeds both RightAgents (`packages/renderer/src/panels/right/RightAgents.tsx:179-183`) and TopBar chips (`packages/renderer/src/shell/TopBar.tsx:372-381`), while the new card tests render with local `allEvents` only. Add direct tests for `accessRequestOpen`/`pendingAccessCountForParticipant`, or a lightweight RightAgents/TopBar integration case with `useStore.upsertEvent`.

## Export Surface

Exporting `extractAccessRequest` is acceptable for this codebase because `autoStream.ts` is already an internal source module and tests already import `runAutoStream` from the same path (`packages/kernel/tests/hooks/autoStream.test.ts:5`). It does widen the emitted declaration surface because kernel builds declarations (`tsconfig.base.json:13`) and there is no `stripInternal`. If the project wants to signal intent, add `/** @internal */` above the export, but that will be documentary unless `stripInternal` is enabled. I would not force an end-to-end `runAutoStream` test just to avoid this export; the access-response polling loop makes pure tests meaningfully cleaner.

## Regressions And Style

- I do not see a regression for existing Gemini shell permission behavior. The command is still extracted from `details.command` (`packages/kernel/src/hooks/autoStream.ts:219`), emitted as `command` (`packages/kernel/src/hooks/autoStream.ts:238`), and rendered ahead of `message` (`packages/renderer/src/cards/AccessRequestCard.tsx:115-119`).
- The fallback helper is consistent with the local defensive-helper style: small `unknown` guards, no schema dependency, and `try/catch` around JSON parsing/stringifying. The main style issue is the inaccurate comment about `post_html.body` (`packages/kernel/src/hooks/autoStream.ts:131-134`) and the overstated "matches every F-Mark MCP tool" claim.
- Minor consistency nit: `extractAccessRequest` accepts `participantId` but does not use it (`packages/kernel/src/hooks/autoStream.ts:170-174`). That is harmless and may be symmetry with other extractors, but it makes the exported function's pure contract look broader than it is.
