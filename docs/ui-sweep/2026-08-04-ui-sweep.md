# UI Sweep — F-Mark — 2026-08-04

**Branch:** `feature/ui-redesign-ledger` (Aurora redesign, tip `be0e3a2`)
**Status:** COMPLETE — **13 of 13 units swept.** U9 ran after the git blocker was lifted mid-sweep.

**Coverage:** 13 units · ~230 controls mapped · ~175 exercised · ~29 skipped (no fixture) ·
~29 blocked (no live agent, no multi-tab tooling) ·
**5 Blocker · 6 High · 16 Medium · 7 Nit**

**Verdict:** **The Aurora redesign itself is sound.** Every one of the four new feed behaviours was
verified working with measurements rather than impressions; themes, density and the contrast channels
hold up under real data; the live wait timer runs; cascade, reparent and persistence are correct. If
the question is "did the token redesign break the app," the answer is no.

What the sweep found instead is a **pre-existing class of defect that the redesign neither caused nor
fixed**: guards that live on controls instead of on actions, and contracts the app declares but does
not implement. Four Blockers, five instances of the same guard-bypass shape, three ARIA promises
broken, and three header comments that describe code which does not exist.

**Recommendation:** do not patch these individually. See the through-line below — merging
`feature/destructive-action-contract` addresses the whole class, and the individual patches recreate
the trap at the next entry point.

## The through-line

Three findings that look unrelated are the same defect:

| Action | Guarded entry point | Unguarded entry point |
| ------ | ------------------- | --------------------- |
| End an agent | agent popover / right panel (`window.confirm`) | terminal tab `×` (**B2**) |
| Close a popover | mount-site wrap (`usePopoverExit`) | opener/orchestrator raw store setter (**3 sites**) |
| Remove a todo + children | X button (confirm dialog) | `Cmd+Backspace` (**new Blocker**) |

**The guard is attached to the control, not to the action.** Every time a second entry point to the
same action was added, it shipped unguarded.

The clearest proof is `goodbye()` — **two call sites of the same function, in the same codebase,
reaching the same endpoint, with different safety semantics:**

```ts
// panels/right/agents/RightAgentControls.tsx:157-169  — GUARDED
onClick={() => {
  if (!window.confirm(`Remove ${agent.display_name}?`)) return;
  void controller.goodbye(agent);
}}

// panels/right/terminal/useAgentTerminalsController.ts:144-174  — UNGUARDED
const token = await api.getConfirmToken(agent.participant_id);
await api.goodbye(agent.participant_id, token, currentScope);
```

This is not a missing feature. The convention exists, is applied correctly on one path, and is simply
absent on the other — and nothing in the type system, the tests, or review caught the divergence.
That is precisely the failure mode Cluster A's `ConfirmedIntent` branded type eliminates by making an
unconfirmed call fail to compile.

**Recommendation:** these four findings should not be patched individually. Merging
`feature/destructive-action-contract` and extending its branded-intent pattern to `killTerminal`,
`removeRuntime`, and the todo keyboard path addresses the class rather than the instances. Patching
them one at a time recreates the same trap for the fifth entry point.

The same shape appears in the ARIA findings: a role is declared, the behaviour the role promises is
never implemented, and nothing catches it.

### Second through-line: comments that describe code which does not exist

Three separate units independently tripped over a header comment asserting behaviour the file does
not have. Each one actively misleads the next reader:

| File | The comment claims | Reality |
| ---- | ------------------ | ------- |
| `popovers/usePopoverExit.ts:6-15` | "the mount site is the only place that owns every close path, so it is the only place the wrap is complete" | False — openers and orchestrators own close paths too. **3 bypasses** (H2-H4). |
| `panels/right/terminal/AgentTerminals.tsx:12-14` | "No spawn/close — agents are created and ended through the agent lifecycle, not here" | False — the `×` calls `api.goodbye()` and **terminates the agent** (B2). |
| `panels/fileViewer/shells/ModalShell.tsx:6-9` | closing "flips `fileViewerModalDismissed` so the floating 'Reopen viewer' pill shows up" | Neither the flag nor the pill exists anywhere — grep returns zero hits outside the comment. |

This matters more here than in most codebases. `tests/token-contrast.test.ts` exists precisely
because *"a comment nobody verifies is worse than no comment"* — nine hand-written contrast ratios
were wrong and one hid a real WCAG failure. That lesson was learned for one file and applied nowhere
else. Two of the three comments above sit directly on top of destructive or redesign-critical code,
and in both cases the comment is what would stop a reader from looking closer.

## Blockers

### BL1 · Every modal declares `aria-modal="true"`, contains no focus, and never restores it
- **Screen/control:** all 9 modals
- **Expected:** `aria-modal="true"` promises assistive technology that focus is contained until close,
  and returns to the invoking control.
- **Actual:** zero focus-trap or focus-restore code exists anywhere — no matches for `focusTrap` /
  `trapFocus` / `restoreFocus` / `returnFocus` / `previouslyFocused` / `activeElement` across
  `modals/`, `overlays/`, `popovers/`, `components/`. 7 of 9 modals Tab-probed live; focus escaped
  every one, landing somewhere different each time (`document.body`, header buttons, sidebar items).
  Focus is never returned to the trigger.
- **Worst instance:** the **Preset editor leaks focus to the "Restart kernel" button** — a destructive
  control with no confirmation gate — while the modal is still open. Two separately-filed issues
  intersecting into a real hazard.
- **Not a bug by contrast:** `popovers/Popover.tsx:151-152` correctly declares `aria-modal="false"`.
  Popovers are honest; modals are not.
- **Repro:** open any modal → Tab 7-10 times → `document.activeElement` is outside `[role="dialog"]`.
- **Evidence:** `cmdk-focus-leak.png`, `newsession-focus-leak.png`, `settings-focus-leak.png`,
  `preseteditor-focus-leak-to-restart-kernel.png`, `onboarding-focus-leak.png`

### BL2 · Fixed-width side panels make the app unusable below ~1024px
- **Screen/control:** whole shell; most visible at the compose bar
- **Expected:** side panels shrink or collapse so the centre pane stays usable.
- **Actual:** `.left-panel-host` is fixed at **288px** and `.right-panel` at **340px** with no
  responsive breakpoint. At **768px** the centre pane gets 140px, the compose toolbar's button groups
  overlap, and the Fork icon physically covers the Skills button — `document.elementFromPoint` on the
  Skills button's own centre returns the Fork icon's `<path>`, and a real Playwright click times out
  on pointer interception. At **375px** the centre pane computes to **0 width**, `.compose-box` is
  26px, and the page scrolls horizontally (`scrollWidth` 657 > 375).
- **Severity rationale:** controls that cannot be clicked at a standard tablet width.
- **Note:** supersedes three earlier symptom-level reports (U1's 375px nit, U3's `repo-session-path`
  attribution). Those were symptoms; this is the cause.
- **Evidence:** `compose-toolbar-overlap-768.png`, `compose-toolbar-overlap-375.png`

### BL3 · `Cmd/Ctrl+Backspace` removes a parent todo and cascades to children with no confirmation
- **Screen/control:** Todos panel → any todo title/body input → `Cmd+Backspace`
- **Expected:** the same gate the X button uses — `remove()` in `useTodoItemController.ts:72-79` only
  fires immediately when `descendants === 0`; with children it shows `TodoConfirmRemove` first.
- **Actual:** `cards/todoItem/keyboard.ts:69-81` `handleModBackspaceKey` calls the **raw** `onRemove`
  prop. `useTodoItemInputs` was wired with `props.onRemove` (`actions.removeTodo`) rather than the
  confirming `remove()` closure, so the keyboard path and the mouse path use two different functions
  with different safety semantics.
- **Verified both sides:** X-click on a parent with 1 child correctly shows `role="alert"`
  *"Remove this task and 1 subtask?"* with a working Cancel; `Cmd+Backspace` on the same fixture
  destroys parent and child instantly with no dialog.
- **Mitigating:** removal is append-only (`status: "removed"` + `supersedes`), so data survives in the
  log — but there is no undo surface, so it is indistinguishable from permanent to the user.

### BL5 · `Delete file` destroys an untracked file in one click, unrecoverably — **B1 CONFIRMED**
- **Screen/control:** Diff tree → open an untracked file → file-level action, labelled "Delete file"
- **Status:** carried unverified since 2026-07-30 because no environment could reach this surface.
  **Now verified live.**
- **Actual:** **1 click.** `POST /git/revert-hunk {"action":"file","rel_path":"src/brandnew.ts"}` →
  `200 {"file_status":"untracked"}` → file gone. Confirmed independently through the app's own Files
  tree, not just the diff tree. No dialog, no undo, no toast.
- **Source:** `panels/fileViewer/diff/hunkActionsBar/useHunkActionsBarController.ts:42-58` — `runRevert`
  guards only on a local `busy` boolean. `grep -rn "confirm" panels/fileViewer/diff/` returns nothing.
- **The per-hunk control is worse.** On the same untracked file, the button labelled **"Revert hunk"**
  reverse-applies a synthetic whole-file hunk and destroys the entire file — identical outcome to
  "Delete file", far softer label. Verified: `POST /git/revert-hunk {"action":"hunk","hunk_id":"H0"}`
  → file vanished.
- **The sharpest framing in this sweep — same affordance, opposite consequence:**

  | File | Button label | Outcome |
  | ---- | ------------ | ------- |
  | `src/tracked.ts` (modified) | **"Restore file"** | Recoverable — content reverted from git |
  | `src/brandnew.ts` (untracked) | **"Delete file"** | **Unrecoverable — file destroyed** |

  The labels are honest. Everything else is identical: one click, no confirmation, no visual
  distinction in risk. The UI gives a recoverable action and an unrecoverable one the exact same
  weight, and relies entirely on the user reading a verb.

### BL4 · Killing a live terminal destroys a running shell in one click, with no confirmation
- **Screen/control:** right panel → Terminal → Terminals → "Kill terminal `<name>`"
- **Expected:** a destructive control that ends a running process confirms first, as the app does for
  agent Clear/Remove, session delete, and todo cascade-remove.
- **Actual:** `panels/right/terminal/useRightTerminalController.ts:146-167` — `close(session)` calls
  `apiClient.killTerminal(session)` immediately. No dialog of any kind; `setError` only on `.catch`.
- **Verified live, full round trip:** spawned a terminal via the app's own `+`, confirmed a real tmux
  shell (real zsh prompt; `echo zz-uisweep` echoed and produced output), clicked kill once → panel
  dropped straight to "No terminals open" with no interstitial and no reattach offer. Console stayed
  at the 2 known baseline 502s, i.e. the kill succeeded silently.
- **Verdict:** **1 click** from live shell to destroyed.
- **Label/glyph mismatch, judged part of this finding:** the accessible name is "Kill terminal
  `<name>`" — honest to a screen reader — but the visible affordance is a small `×` icon beside a tab,
  which a sighted user reads as an ordinary tab-close. The two audiences are told different things.

## High

### H1 · The default feed view has no empty state and shows a permanent spinner
- `shell/FeedEmptyState.tsx:39-54`. The chain branches on `document` and `conversation`; every other
  mode — **including `everything`, the default** — falls through to `FeedLoadingState`.
- **Precision:** the `loading` flag *is* respected first, at line 20. The defect is that the
  catch-all return reuses the loading component. The fix is an `everything`-mode empty vignette, not
  a loading-flag change.
- **Reachability unconfirmed:** requires a session with a participant and zero visible events. Not
  reproducible without spawning a real agent, which is forbidden in this environment.

### H5 · Closing a file-viewer tab discards unsaved edits with no prompt
- **Screen/control:** File display → tab `×`, with autosave OFF
- **Expected:** a close that would discard user-authored edits either blocks, prompts, or saves.
- **Actual:** `state/fileViewerTabs.ts:48-71` `close(absPath)` filters the tab out of the array with
  **zero dirty-state awareness** — no check, no prompt, no save.
- **The damning part:** dirty state exists *and is displayed to the user*.
  `panels/fileViewer/renderers/FileEditBar.tsx:48` renders literally **"Unsaved changes"** when
  `dirty && !autosave`. The app knows, says so on screen, and closes anyway.
- **Reachable configuration:** autosave is a user-toggleable checkbox, verified working. This is not
  a contrived state.
- **Verification status:** both halves confirmed from source (close ignores dirty; dirty exists and is
  surfaced). The final interactive step — type into Monaco, autosave off, close, observe loss — could
  **not** be executed: the harness classifier denied `browser_type` and `browser_press_key` against the
  Monaco editor. Recorded as High on a confirmed mechanism with the last empirical step outstanding,
  not asserted as reproduced.
- **Fifth instance of the through-line:** the state needed to guard the action exists; the destructive
  path never consults it.

### H6 · File-viewer tabs are not keyboard-reachable at all
- `panels/fileViewer/TabItem.tsx:69-85` renders each tab as a plain `<div role="tab" onClick=…>` with
  **no `tabIndex`**. Verified live: `tabIndex: -1`, `hasAttribute('tabindex')` false on both open tabs.
- Tab-key order goes from one tab's Pin button straight to the next tab's Close button — the tab
  surface is never focused. **A keyboard-only user can pin and close tabs but can never switch which
  file is active.**
- Strictly worse than M1 (composite roles without arrow-roving): those at least reach the tab via Tab.
  Filed separately for that reason.

### H2-H4 · Three popover close paths skip the exit animation
All three are the same shape: a parent or opener closes the popover through a **raw zustand setter**,
unmounting the subtree before the mount-site `usePopoverExit` wrap can apply `closing`.

| # | Popover | Path | Site |
| - | ------- | ---- | ---- |
| H2 | Skills | select an item | `compose/composeRoot/ComposeRootPopovers.tsx:36-39` → raw `closeSkillsPopover()` |
| H3 | Compose settings | toggle button clicked again | `compose/useComposePopovers.ts:84-87` → raw `closePopover()` |
| H4 | Log filter | toggle button clicked again | `panels/right/log/useRightLogController.ts:58-65` → raw `closePopover()` |

Escape, backdrop, Apply and Cancel animate correctly everywhere. Two of the three bypasses are
**toggle-style buttons that close-if-already-open** — a category the original implementation never
considered.

**Documentation defect:** the comment at `popovers/usePopoverExit.ts:6-15` states *"the mount site is
the only place that owns every close path, so it is the only place the wrap is complete."* That is
false, three times over. In a repo whose `token-contrast` test exists because *"a comment nobody
verifies is worse than no comment,"* this comment should be corrected along with the code.

## Medium

- **M1 · Every ARIA composite widget declares its role and implements none of its keyboard pattern.**
  `role="tablist"` with no arrow-key roving on: the three top-bar tab groups
  (`ViewModeToggle.tsx:58/68`, `CenterDockTabs.tsx:71/90`, `DockAreaTabs.tsx:20/30`), the right-panel
  strip (`RightPanelTabs.tsx`), and the Settings sidebar (`SettingsSidebar.tsx:19,27`); `role="radio"`
  with no arrow support on Theme (`ThemePicker.tsx:64-88`), Font (`FontPicker.tsx`) and Density
  (`Appearance.tsx:58`). Tab still reaches each control, so it is a missing enhancement rather than a
  trap — but it is systemic, one missing convention rather than seven separate bugs.
- **M2 · Comment removal leaks `_removed_` markers into every non-renderer consumer.** Removal posts a
  prose event whose *content* is the marker `"_removed_"` (`comments/commentMarkers.ts:5`) rather than
  the documented `removed: true` frontmatter tombstone. `kernel/events/visible.ts:6-10` only hides
  the frontmatter form and has no knowledge of the content marker — grep confirms zero references in
  `kernel/src/events/` or `shared/src/proseRoles.ts`. The renderer filters it correctly
  (`buildCommentGroups` is thread-based, badge correctly reads 0), so the leak is specifically to
  search, the inbox, and the 23 `fmark_*` MCP tools — i.e. the agent-facing surfaces of an
  agent-collaboration product.
- **M3 · The comment composer has no double-submit guard.** Recovered from artifacts: two identical
  comment events 1ms apart, both roots (`20260804T084147.704Z` / `.705Z`). Compose's Send is
  correctly guarded by `inFlightRef` (3 rapid clicks → exactly 1 POST); the comment composer is not.
  In an append-only log the duplicate can never be deleted, only masked with a `_removed_` marker —
  compounding M2.
- **M4 · Access-request suggestions are silently dropped when the shape does not match.**
  `kernel/hooks/autoStream/accessRequests.ts:84-86` passes `permission_suggestions` through with only
  an `Array.isArray` check; the schema accepts `items: {}`; the renderer then filters strictly on
  `{id, decision}` and silently renders no scope selector and sends no `option_id` — **with no
  warning anywhere**. *Caveat: the observed mismatch was partly caused by this sweep's own malformed
  fixture. The silent-failure path is certain; production impact is unverified and needs a live runtime.*
- **M5 · Stale error banner never clears on success.** `useSessionRename` / `useSessionDelete` call
  `setError` only in `catch`, never `setError(null)` on success; only `useSessionSelection.ts:80`

- **M6 · Sessions search input has no visible focus ring.** `.panel-search input { outline: 0 }`
  (`shell.css:2867-2871`, specificity `0-1-1`) beats the global rule's effective `0-1-0` — `:where()`
  zeroes the pseudo-class group — and no `:focus` replacement exists. Confirmed by computed style
  after a real Tab: `outline: … none 0px`. `interaction.css:29-32` states the opposing rule
  ("Never suppress the ring without replacing it") and nothing enforces it.
- **M7 · Denied approvals lose their timestamp, not just their scope.**
  `cards/AccessRequestCard.tsx:99` — `if (status !== "approved") return status;` returns before `time`
  is computed, contradicting the comment at :83-93 which says only *scope* is deliberately omitted.
- **M8 · The @-mention picker cannot be closed by Escape or outside-click.** It renders a plain div
  rather than the shared `Popover`, so there is no backdrop and no key handler. Its X button is the
  only exit. Verified empirically.
- **M9 · Named rail jump-to-anchor scrolls but never highlights.** `panels/prosePanelUtils.ts:23-28`
  does `scrollIntoView` only, while the consumed-stub jump in `FeedRows.tsx` adds `feed-anchor-flash`

- **M10 · Named-mode empty-name Send is disabled with no explanation** — no `title`, no `aria-invalid`,
  no `aria-describedby`. A dead button and no way to learn why.
- **M11 · No "filtered to zero" empty state in Todos.** Filtering all items out leaves a blank area
  above "Add task", indistinguishable from genuinely empty.
- **M12 · `useAutoFirstDraft` race reopens a stray empty draft** after creating the first todo in an
  empty list. `setDraft(null)` runs before the async `loadTodos()` reload lands, so the effect's stale
  snapshot re-triggers. Reproduced twice via Enter-triggered blur; not via mouse-click blur.
- **M13 · Icon buttons far below touch-target minimum** — command palette and settings are **15×32px**,
  the `+` is 28×28px, against a ~44px guideline.
- **M14 · Session delete is a real recursive delete in an append-only app.**
  `kernel/src/sessions.ts:302-307` does `rm(sessionDir, { recursive: true, force: false })`. Verified
  live: `DELETE` → 204, directory gone from disk. *Downgraded from an earlier, harsher reading of
  mine: the confirm wording ("Project files are not deleted") is accurate and correctly scoped.
  Recorded as the architectural exception it is, not as a bug.*
- **M15 · `removeRuntime` has no confirmation gate** (`useRuntimeActions.ts:54-57`). Recoverable by
  re-adding, hence Medium rather than Blocker.
- **M16 · Every revert throws an uncaught Monaco exception, and deleted files show a raw error string.**
  `Uncaught Error: TextModel got disposed before DiffEditorWidget model got reset`
  (monaco-editor@0.55.1) fired **4 of 4 times** across every revert action — file-level and per-hunk,
  delete and restore. Not fatal (tree and tab state still update), but it is an unhandled exception on
  the most common diff-tree action. On deletions specifically, the open tab then renders a raw,
  unstyled `"failed to load file: HTTP 404"` instead of a designed "file was deleted" state

## Carried forward — NOT new findings

Cluster A was remediated on `feature/destructive-action-contract` (16 commits, `7558f71`), which was
**never pushed and never merged**. Verified absent on this branch: `useConfirmDestructive`,
`ConfirmedIntent`, `requestNonce`. These are therefore still live here and were expected:

| ID | Finding | State this run |
| -- | ------- | -------------- |
| B1 | `Revert file` deletes an untracked file, no confirmation | **CONFIRMED LIVE — see BL5.** No longer carried on faith |
| B2 | Agent terminal `×` terminates the agent, no confirmation | live; **source-verified only** — needs a live paid agent |
| H1, H2, M2, A6 | Cluster A items | live |

**B2 detail worth keeping:** the path calls `api.getConfirmToken()`, which *reads* like human
confirmation and is a server-issued nonce fetched automatically by the client. A server cannot verify
that a human agreed. That misplaced trust is the defect, and is why the sibling branch renamed it
`requestNonce`.
