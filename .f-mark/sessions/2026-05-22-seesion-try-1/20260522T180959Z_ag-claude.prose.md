# F-Mark architecture

## The one-line thesis

**The filesystem is the protocol.** A collaboration session is a folder of timestamped, append-only event files. There is no database, no central document, no message queue — just files. A renderer projects the folder into a UI; agents contribute by POSTing structured payloads that the kernel turns into files.

## The four design moves that fall out of that

**1. Append-only with supersessions.** Files are never edited. To revise, you write a new file containing a `supersedes` pointer to the old one. The renderer hides superseded files by default and shows them in a history view. Snapshots are `cp -r`, branches are folder copies, sharing is `zip`, version control is `git` — for free.

**2. Filename as schema.** Every event file is named `{ISO_TIMESTAMP}_{PARTICIPANT_ID}.{KIND}.{EXT}` — e.g. `20260522T180550Z_ag-claude.prose.md`. The filename carries the sort key, the author, and the type. Listing a directory tells you the whole story of a session. Participant ids are prefixed (`us-` for humans, `ag-` for agents) so you can tell who said what at a glance.

**3. A tiny event vocabulary, with variants in the *data*, not the kind.** There are only a handful of kinds: `prose`, `choices`, `choice`, `todo`, `turn-end`, `html`, `file`. The clever move is in `prose`: one kind serves casual messages, durable named contributions (like this one), and inline comments — the difference is just which optional frontmatter fields are present (`name`, `target`, `in_reply_to`, `supersedes`). New variants don't need new kinds.

**4. The agent surface is uniformly POST.** No PATCH, no PUT. Every contribution is `POST /sessions/:id/events/<kind>` with a JSON body containing `participant_id`. Reads are `GET /events?since=<ts>` — stateless, the kernel doesn't track who's seen what. Agents pass their own watermark. The protocol fits on a postcard.

## What the kernel does

The kernel is a thin Fastify server. It validates the payload, writes a file with the right name to the right session folder, and broadcasts the new filename over a WebSocket. That's it. No business logic about "conversations" or "threads" — those are renderer concepts derived from the log.

## What the renderer does

The renderer is a *projection*. It reads the folder, sorts by timestamp, applies supersessions, then derives:

- a chronological feed (visible, non-comment events)
- a list of named contributions (prose with `name`)
- comments grouped by their target file (prose with `target`)
- open/done todos, choice answers, current-turn participant

Multiple renderers could project the same log differently — a doc-style view, a chat-style view, a kanban — all reading the same files.

## The turn model

There's no central "whose turn is it" state. It's *derived* from the latest `turn-end.json` event in the folder. If the latest one is from an `ag-` participant, it's the user's turn. If it's from a `us-` participant, it's an agent's turn. Post-POC this extends naturally to n-party routing.

## Why it's shaped this way

The whole architecture is organized around minimizing what an agent has to learn. The agent's loop is: read events since I last checked, decide, POST events, POST turn-end. No SDK, no schema migration, no "document model" to keep in sync. A bash script with `curl` and `jq` is a fully-capable F-Mark agent. That low ceiling on agent complexity is what makes the system extend cleanly to multi-agent, hooks, and (later) cloud sync — every layer added is just more code reading the same files.
